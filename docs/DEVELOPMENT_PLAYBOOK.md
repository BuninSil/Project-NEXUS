# NEXUS DEVELOPMENT PLAYBOOK — HANDOFF FOR EVERY SESSION

Этот документ нужен, чтобы владелец и любой будущий помощник продолжали разработку с правильного места, не придумывали заново архитектуру и не путали планы с готовыми функциями.

## 1. Обязательное чтение перед работой

В начале каждой новой рабочей сессии:
1. Прочитать этот файл.
2. Прочитать `docs/PROJECT_SPEC.md` — главный документ требований.
3. Прочитать `docs/EVOLVING_INTELLIGENCE.md`, `docs/ARCHITECTURE.md` и `docs/ROADMAP.md`.
4. Прочитать `docs/SESSION_STATE.md` — актуальное состояние и следующий шаг.
5. Проверить текущую ветку, последние коммиты и фактическое состояние файлов в GitHub. Не полагаться только на память чата.

Если документы противоречат друг другу, не угадывать: сообщить о конфликте и согласовать приоритет. Главный продуктовый источник — PROJECT_SPEC; текущий факт реализации — код и SESSION_STATE; порядок работ — ROADMAP.

## 2. Правила совместной разработки

- Работать маленькими законченными шагами с проверяемым результатом.
- Перед изменением читать текущую версию файла и учитывать существующий код.
- Не переписывать архитектуру ради красивой схемы без конкретной необходимости.
- Не добавлять функции вне ближайшего этапа roadmap, если они блокируют или размывают текущую задачу.
- Не создавать десятки файлов без работающего вертикального сценария.
- Предпочитать понятные решения, совместимые с ограниченным оборудованием.
- Пользователю давать конкретные команды и точные места, куда нажать/вставить; не перегружать развилками.
- Для кода по возможности давать цельные файлы или точные патчи, а не фрагменты без контекста.
- Не предполагать, что команда выполнена: ждать вывода пользователя или результата инструмента.
- Не утверждать, что тесты прошли, приложение запустилось или файл изменён, пока это не подтверждено.
- Не выдавать созданную документацию за реализованную функциональность.
- Сначала делать резервную копию/проверять diff перед рискованными изменениями.
- Не хранить ключи, пароли, личную память и базы данных в Git.

## 3. Технические правила проекта

- Основной язык: Python 3.11+ на текущем этапе.
- API: FastAPI.
- Начальное хранилище: SQLite; миграции должны быть предусмотрены до усложнения схемы.
- Внешние модели: только через адаптеры; ни один провайдер не обязателен.
- Целевое ядро должно запускаться без LLM credentials и без интернета, предоставляя ограниченный, но честный функционал.
- Не внедрять тяжёлые зависимости на HP 250 G7 без необходимости.
- Не добавлять Docker как обязательное требование для локального старта.
- Секреты через переменные окружения или защищённое хранилище.
- Любой инструмент агента — отдельный интерфейс с allowlist, параметрами, проверкой прав, логированием, тайм-аутом и бюджетом.
- Любая функция памяти должна иметь тесты на корректное сохранение, извлечение, изоляцию и удаление.
- Любой research ingestion обязан хранить происхождение данных и считать внешний контент недоверенным.
- Обучение весов — отдельная воспроизводимая команда/задача, а не побочный эффект обычного чата.

## 4. Обязательный цикл каждой задачи

1. **Orient:** сверить SESSION_STATE, roadmap, код и ограничения оборудования.
2. **Define:** сформулировать один небольшой результат и критерии готовности.
3. **Inspect:** прочитать файлы, которые будут затронуты; проверить зависимости и совместимость.
4. **Implement:** внести минимальные связанные изменения.
5. **Verify:** выполнить подходящие тесты/линтер/ручной запуск. Если проверить нельзя — явно записать это.
6. **Review:** проверить diff, безопасность, секреты, документацию и обратную совместимость.
7. **Record:** обновить roadmap, SESSION_STATE и соответствующую документацию.
8. **Handoff:** оставить одну точную следующую задачу с командами/ожидаемым результатом.

## 5. Статусы

Использовать только честные статусы:
- **Planned** — идея описана, работы нет.
- **In progress** — работа начата, критерии не выполнены.
- **Implemented, unverified** — код написан, но не проверен.
- **Verified** — проверка выполнена, указаны команда и результат.
- **Blocked** — есть конкретное препятствие.

Не ставить галочку только за наличие файла или кода.

## 6. Принцип работы с обучением

Не смешивать:
- историю разговоров;
- подтверждённую память;
- кандидаты в обучающие примеры;
- датасеты;
- версии весов модели.

Никакое личное сообщение не используется для обучения без отдельного явного согласия. Никакая веб-страница не меняет системные инструкции или веса автоматически. Обучение должно иметь версию данных, параметры, метрики, тесты безопасности и способ отката.

## 7. Принцип работы с агентностью

Начинать с read-only. Затем разрешать создание черновиков в отдельной рабочей папке. Запуск команд — только через список разрешённых операций и с ограничениями. Удаление, публикация, отправка сообщений, изменение настроек, финансовые и иные внешние/необратимые действия требуют подтверждения владельца. Всегда должна быть возможность остановить задачу.

## 8. Обновление состояния проекта

После каждой рабочей сессии обновить `docs/SESSION_STATE.md`:
- текущая версия/этап;
- что реально сделано;
- какие файлы изменены;
- какие проверки выполнены и их точный результат;
- что не проверено или сломано;
- блокеры и решения;
- одна следующая задача;
- точные команды/шаги для продолжения.

Сохранять только краткое оперативное состояние, а не копировать туда всю спецификацию.

## 9. Как начинать новую сессию с владельцем

Сначала кратко сообщить:
- на каком этапе проект;
- что подтверждено как работающее;
- какая одна задача следующая.

Если пользователь пишет «продолжим», не просить заново пересказывать проект. Сначала сверить репозиторий и документы. Если компьютер недоступен, можно продолжать проектирование или подготовку кода, но честно обозначить, что runtime-проверка отложена.

## 10. Приоритет на текущий момент

Не начинать с обучения собственной большой LLM. Ближайшая цель — запустить существующий v0.1 scaffold на HP 250 G7, выполнить smoke tests, затем отделить orchestration от обязательного LLM endpoint и реализовать честный model-independent fallback. После этого — durable memory.

Большая цель остаётся PROJECT_SPEC; текущая задача определяется ROADMAP и SESSION_STATE.
